# Database Schema (Beginner Friendly)

Post-002 ground truth. Apply order on a fresh DB: `hepziba_schema.sql` → `backend/sql/001_hospital_alignment.sql` → `backend/sql/002_fix_doctors_and_constraints.sql` (all idempotent; 002 is safe to re-run).

## 1. Users Table
All people who log into the system—patients, doctors, admins.

| Field | Type | Description |
|---|---|---|
| id | serial PK | Unique user ID |
| name | text NOT NULL | Full name |
| email | text UNIQUE NOT NULL | Login email (lowercased by API) |
| password | text NOT NULL | Hashed password |
| role | text NOT NULL CHECK IN ('patient','doctor','admin') | RBAC role |
| active | boolean DEFAULT TRUE | Soft-deactivate flag (`login` rejects `active=false`; backfilled TRUE where NULL by 002) |
| email_verified | boolean DEFAULT FALSE | Email verification state |
| verification_code | text NULL | Email verification code |
| verification_code_expires_at | timestamp NULL | Code expiry |
| reset_code | text NULL | Password-reset code |
| reset_code_expires_at | timestamp NULL | Reset code expiry |
| created_at | timestamp DEFAULT NOW() | When account made |
| updated_at | timestamp DEFAULT NOW() | Last update (maintained by API, not trigger) |

## 2. Patients Table
Clinic patients — one row per patient user.

| Field | Type | Description |
|---|---|---|
| id | serial PK | Unique patient ID |
| user_id | int UNIQUE FK → users(id) ON DELETE CASCADE | Linked user (UNIQUE added by 002; required for `ON CONFLICT (user_id)` upserts in auth) |
| patient_code | text UNIQUE NULL | Random non-sequential code (`HEP-` + 6 Crockford-base32 chars, e.g. `HEP-7KQ2XD`; generated by API, DB-checked unique; legacy codes stay valid) |
| dob | date NULL | Date of birth |
| age | integer NULL | Age |
| sex | text NULL | Sex |
| allergies | text NULL | Allergies info |
| contact | text NULL | Legacy contact field (prefer `mobile`) |
| mobile | text NULL | Phone, 10–15 digits (validated by API) |
| address | text NULL | Address |
| photo_url | text NULL | Photo URL |
| aadhar_number | text NULL | 12-digit Aadhar (validated by API) |
| height_cm | numeric(5,2) NULL | Height |
| weight_kg | numeric(5,2) NULL | Weight |
| bp | text NULL | Blood pressure |
| spo2 | integer NULL CHECK 0–100 | SpO2 (CHECK added by 002) |

## 3. Doctors Table (added by 002; required — was missing)
Doctor profiles — one row per doctor user. All doctor-facing controllers (`doctors/*`, `appointments/*`, `prescriptions/*`, `admin/*`) join through this table.

| Field | Type | Description |
|---|---|---|
| id | serial PK | Doctor profile ID — this is what `appointments.doctor_id` and `prescriptions.doctor_id` reference |
| user_id | int UNIQUE NOT NULL FK → users(id) ON DELETE CASCADE | Linked doctor user |
| specialty | text NULL | Specialty |
| phone | text NULL | Phone |
| bio | text NULL | Bio |
| created_at | timestamp DEFAULT NOW() | When profile created |

Doctor lookup pattern used by the API: `SELECT id FROM doctors WHERE user_id=$1`. Patient booking accepts either `doctors.id` or `users.id` and resolves to `doctors.id`.

## 4. Appointments Table

| Field | Type | Description |
|---|---|---|
| id | serial PK | Unique appointment ID |
| patient_id | int FK → patients(id) ON DELETE CASCADE | Who is being seen |
| doctor_id | int NULL FK → doctors(id) ON DELETE SET NULL | Which doctor profile (retargeted from `users(id)` by 002, with legacy `users.id` values backfilled to `doctors.id`) |
| scheduled_at | timestamp NULL | Canonical booking time (added by 001, backfilled from `date_time` by 001/002) |
| date_time | timestamp NULL | Legacy booking time (kept for compat; 001 drops NOT NULL; 002 backfills both directions so `COALESCE(scheduled_at, date_time)` always works) |
| token_number | integer NULL | Daily per-doctor token (added by 001) |
| status | text DEFAULT 'pending' CHECK IN ('pending','confirmed','done','cancelled') | Status (CHECK added by 002) |
| reason | text NULL | Why the visit |
| notes | text NULL | Slot/remarks |

Invariant (CHECK `appointments_scheduled_at_check`, added when data allows): `scheduled_at IS NOT NULL OR date_time IS NOT NULL`. Controllers read via `COALESCE(scheduled_at, date_time)` and dual-write both columns on insert.

## 5. Prescriptions (added by 001, repaired by 002 if 001 aborted early)

| Field | Type | Description |
|---|---|---|
| id | serial PK | Prescription ID |
| appointment_id | int FK → appointments(id) ON DELETE CASCADE | Source appointment |
| doctor_id | int FK → doctors(id) ON DELETE SET NULL | Prescribing doctor profile |
| patient_id | int FK → patients(id) ON DELETE CASCADE | Patient |
| doctor_name | text NULL | Denormalized doctor name |
| prescribed_on | timestamp DEFAULT NOW() | When prescribed |
| notes | text NULL | Notes |

`prescription_items`: `id PK`, `prescription_id FK → prescriptions(id) CASCADE`, `medicine_name NOT NULL`, `dosage_morning/afternoon/evening/night BOOLEAN DEFAULT FALSE`, `before_food/after_food BOOLEAN DEFAULT FALSE`, `quantity INT`, `instructions TEXT`.

## 6. Billing (added by 001, repaired by 002 if needed)

`invoices`: `id PK`, `patient_id FK → patients(id) CASCADE`, `appointment_id FK → appointments(id) SET NULL`, `doctor_name TEXT`, `invoice_date DEFAULT NOW()`, `total_amount NUMERIC(12,2) DEFAULT 0`, `status TEXT DEFAULT 'unpaid'`.
`invoice_items`: `id PK`, `invoice_id FK → invoices(id) CASCADE`, `medicine_name NOT NULL`, `expiry_date DATE`, `unit TEXT`, `mrp NUMERIC(10,2) DEFAULT 0`, `quantity INT DEFAULT 1 CHECK >= 0`, `total NUMERIC(10,2) DEFAULT 0`.

## 7. Inventory (added by 001)

`inventory_items`: `id PK`, `name NOT NULL`, `category TEXT`, `stock INT DEFAULT 0 CHECK >= 0`, `reorder_level INT DEFAULT 0`, `unit TEXT`, `updated_at DEFAULT NOW()`.

## Example Relationships
- Every patient row links to exactly one `users` row (`role='patient'`); `patients.user_id` is UNIQUE.
- Every doctor row links to exactly one `users` row (`role='doctor'`); `doctors.user_id` is UNIQUE.
- Appointments link `patients.id` → one `doctors.id` (NOT `users.id` since 002).
- Prescriptions link one appointment + one patient + one doctor profile.
- Invoices link one patient (+ optional appointment); invoice_items belong to one invoice.
- Soft delete: `admin` sets `users.active=false`; rows are kept.

## Indexes (002)
`idx_appointments_doctor_scheduled_at`, `idx_appointments_patient_id`, `idx_appointments_doctor_id`, `idx_patients_user_id`, `idx_doctors_user_id`, `idx_prescriptions_{patient,doctor,appointment}_id`, `idx_prescription_items_prescription_id`, `idx_invoices_{patient,appointment}_id`, `idx_invoice_items_invoice_id`, `idx_users_role_active`.

## How to Apply (First Time, in order)
```bash
psql -U your_username -d your_database_name -f hepziba_schema.sql
psql -U your_username -d your_database_name -f backend/sql/001_hospital_alignment.sql
psql -U your_username -d your_database_name -f backend/sql/002_fix_doctors_and_constraints.sql
```
Re-running 002 is safe (idempotent). Known quirk: 001 references `doctors(id)` before 002 creates `doctors`, so on a truly fresh DB 001 errors at `prescriptions` (`relation "doctors" does not exist`) after applying its earlier ALTERs; 002 then creates `doctors` and any missing 001 tables. See `backend/sql/README.md` for verification steps.
